# Raft

Выбор лидера и репликация строковых команд с фиксированным составом кластера.
Состояние хранится в памяти. Команды сохраняются в журналах узлов как строки,
а фиксация записей отслеживается через `commitIndex`.

В обычной репликации `matchIndex` не уменьшается, а `nextIndex >= matchIndex + 1`.
Для возвращающегося пустого узла предусмотрен отдельный режим восстановления:
он включается при актуальном отказе на уже подтверждённом `prevLogIndex = matchIndex > 0`.
Исторический `matchIndex` сохраняется, но до успешной полной пересылки этот узел
не учитывается при подсчёте подтверждений для фиксации. Сетевой таймаут не включает
режим восстановления. Состояние восстановления относится к текущему term лидера.

При обычном несовпадении follower возвращает `conflictIndex`: первый отсутствующий
индекс или начало группы записей с конфликтующим term. Это позволяет быстрее
найти общий префикс без отдельного запроса на каждую пропущенную запись.

Восстановление пустого узла — расширение для текущей модели хранения в памяти.
Постоянного хранения `currentTerm`, `votedFor` и лога пока нет: восстановление от
работающих реплик не заменяет сохранение состояния. Одновременный перезапуск
всех узлов теряет данные.

## Запуск

Нужна Java 25. Запустить по одному процессу в трёх отдельных терминалах:

```sh
bash gradlew bootRun --args='--node.id=1 --server.port=8081'
bash gradlew bootRun --args='--node.id=2 --server.port=8082'
bash gradlew bootRun --args='--node.id=3 --server.port=8083'
```

Проверить роль узла и его журнал можно через `GET /raft/status`.

## Добавление команд

Отправлять запрос нужно на узел со статусом `LEADER`:

```sh
curl -i http://localhost:8081/raft/add_entries \
  -H 'Content-Type: application/json' \
  -d '{"entries":["first","second"]}'
```

Лидер добавляет весь пакет с текущим term и запускает репликацию.
Строки сохраняются без интерпретации и изменения.

| HTTP-код | Значение |
|---|---|
| `202 Accepted` | Пакет принят в лог; фиксация пока не подтверждена (`committed: false`). |
| `200 OK` | К моменту ответа весь пакет уже зафиксирован (`committed: true`). |
| `409 Conflict` | Узел не является лидером; лог не изменяется. |
| `400 Bad Request` | Отсутствует список команд, список пуст или содержит `null`, либо JSON некорректен. |

Ответ содержит поля `status` (например, `"202 ACCEPTED"`) и `committed`.
Ответ `202` не гарантирует последующую фиксацию: незафиксированный хвост может
быть заменён после смены лидера. Автоматической переадресации на лидера нет.

## Состояние узла и журнал

```sh
curl http://localhost:8081/raft/status
```

Пример ответа:

```json
{
  "nodeInfo": {"id": 1, "port": 8081, "host": "localhost"},
  "status": "LEADER",
  "currentTerm": 1,
  "peers": [
    {"id": 2, "port": 8082, "host": "localhost"},
    {"id": 3, "port": 8083, "host": "localhost"}
  ],
  "entries": [
    {"term": 1, "command": "first"},
    {"term": 1, "command": "second"}
  ],
  "commitIndex": 2
}
```

Индекс Raft — позиция записи в массиве плюс один. Записи с индексами до
`commitIndex` включительно зафиксированы. Метод доступен на любом узле и
возвращает согласованный снимок его локального состояния; отстающий follower
может показывать более короткий лог или меньший `commitIndex`.

## Логирование репликации и фиксации

На уровне INFO выводятся разные события:

- `Replicated entries from leader` — follower сохранил новые записи (диапазон индексов и количество).
- `Replication confirmed by follower` — лидер получил подтверждение записей от follower.
- `Committed log through index` — продвинулся `commitIndex`.

Heartbeat и повторная передача уже имеющихся записей не логируются как новая
репликация. Начало полного восстановления выводится на уровне WARN, завершение — INFO.

## Тесты

```sh
bash gradlew test
```

Тесты проверяют переходы состояний, выборы, актуальность лога кандидата,
приём и отправку RPC, исправление конфликтов, фиксацию по большинству,
запоздавшие ответы, восстановление без уменьшения `matchIndex`,
события логирования и REST API. HTTP-транспорт в unit-тестах подменяется,
поэтому запуск отдельных узлов не требуется. Отдельный тест проверяет
загрузку Spring-контекста с подменённым сетевым сервисом.

## Проверка 1000 команд на реальных узлах

```sh
bash gradlew bootJar
python3 scripts/check_replication_load.py --count 1000
```

Нужны Python 3, Java 25 или новее и свободные порты 8081–8083. Путь к Java можно
передать через `--java /path/to/bin/java`. Скрипт запускает три процесса и проверяет:

1. Добавление 1000 команд одним пакетом и фиксацию на всех репликах.
2. Перезапуск follower с пустым состоянием и восстановление без новых выборов.
3. Ещё 1000 команд отдельными последовательными POST-запросами.
4. Совпадение журналов и `commitIndex`, а также монотонное продвижение
   зафиксированного индекса в событиях логирования каждого процесса.

Результаты и процессные логи сохраняются в `build/reports/replication-load-check/`.
После проверки скрипт останавливает только созданные им процессы. Измерения
относятся к коротким строковым командам и трём локальным процессам на одной машине.
